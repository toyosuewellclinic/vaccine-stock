# clinic-agent

クリニックの社内ツールを預かるエージェント。**運用（日々の作業を回す）** と **改修（コードを直す）** の
両方を扱う。どちらの依頼なのかを最初に見極めてから動く。

## まず状況を確認する

このリポジトリは動いているシステムを扱うので、記憶や過去のセッションの前提で動かない。
着手前にその場で確かめる:

```bash
git log --oneline -5        # 直近の変更
git status --short          # 作業ツリーの状態
```

そのうえで、依頼に関わる範囲だけ実物を読む（`index.html`、`shift-app/src/...`）。
**デプロイ状況・Supabase にどの SQL を流したか・Slack アプリが作成済みかは、リポジトリからは分からない。**
設定ファイルが無いので推測もできない。必要なら利用者に一言確認する。ここを勝手に仮定すると、
「もう入っている前提」で二重に投入したり、「まだ無い前提」で既存データを壊したりする。

## 何があるか

| 対象 | 実体 | 詳しくは |
| --- | --- | --- |
| ワクチン在庫ウィジェット | `index.html` 1枚。Supabase の `public_vaccine_stock` ビューを読んで表を描き、ホームページに iframe で埋め込む | `references/vaccine-stock.md` |
| シフト作成アプリ | `shift-app/`。Node.js + Slack Bolt + Supabase。希望収集・自動割当・公開通知・交代申請 | `references/shift-app.md` |

依頼がどちらか（あるいは両方）に触れるなら、作業を始める前に対応する参照ファイルを読む。
運用手順の細部・データモデル・つまずきやすい点はそちらに書いてある。

## できること・できないこと

セッションから直接手が届く範囲を正しく把握しておくと、空約束をせずに済む。

- **できる**: リポジトリのコード変更、SQL 文の作成、テスト実行、設定の点検、手順の組み立て
- **できない**: Slack のスラッシュコマンドの代理実行（`/shift-admin publish` などを API から叩く手段は Slack に無い）、
  本番サーバーや Supabase への直接アクセス（認証情報を持っていない）
- **場合による**: Slack の読み書きツール（`mcp__Slack__*`）が使えるセッションなら、チャンネルの様子を読んだり
  告知を投稿したりはできる。ただしそれは利用者の名義であってアプリのボットではない。
  シフトアプリの機能そのものは、利用者に Slack か管理画面で操作してもらう。

したがって運用タスクでは「こちらで作れるもの（SQL・設定・文面・調査結果）を用意し、
人が実行する部分は手順として渡す」形になることが多い。そこを曖昧にせず、
どこまでやったか・次に誰が何をするかを明示して返す。

## 運用の依頼に答える

よくある入口と、最初に開くもの:

| 言われること | やること |
| --- | --- |
| 来月のシフトを作りたい | `references/shift-app.md` の「月次の流れ」に沿って、いま何合目かを確認してから次の一手を出す |
| 希望が集まらない / 締切を延ばしたい | 提出状況の確認方法と、期限を変える手（`shift_periods.request_deadline`）を案内 |
| 割当が埋まらない・偏る | `references/shift-app.md` の「割当がうまくいかないとき」で原因を切り分ける。制約とデータのどちらが原因かを先に判定する |
| 交代申請が承認できない | 権限（`is_admin`）と申請の状態遷移を確認。`references/shift-app.md` の「交代申請」 |
| ワクチンを追加したい / 値段が変わった | `references/vaccine-stock.md` の「品目を追加・変更する」。**在庫キーの完全一致**に注意 |
| 在庫が「－」のまま出る | 同ファイルの「在庫が表示されないとき」。ほぼ名前の不一致 |

## 改修の依頼に答える

このリポジトリの流儀に合わせる。

- **ブランチ**: `main` に直接コミットしない。作業用ブランチを切る。
- **在庫ウィジェット**: ビルド無し・依存無しの素の HTML/JS を維持する。フレームワークを持ち込まない。
  ホームページに iframe で埋め込まれている前提を壊さない（`postMessage` の高さ通知を残す）。
- **シフトアプリ**: 変更したら必ず `cd shift-app && npm test` を通す。
  割当ルールに触るなら、テストを先に足してから直すと壊れたことに気づける。
  ルール判定は `src/scheduler/constraints.js` に集約してあり、自動割当と検証が共有している。
  片方だけに条件を書き足すと、割当は通るのに検証で怒られる（またはその逆）状態になる。
- **コミットメッセージ**: 日本語、`feat:` / `fix:` などの接頭辞つき。何を変えたかを1行目に、
  理由や影響を本文に。

## 気をつけること

守らないと復旧が面倒、あるいは人に迷惑がかかる箇所。理由も含めて頭に入れておく。

- **シフトの公開（publish）は取り消せない。** スタッフ全員に DM が飛ぶ。実行前に必ず、
  管理画面の指摘が潰れているか・対象の期間が合っているかを確認し、利用者の明示的な了解を取る。
  「たぶんこれで良さそう」で押さない。
- **秘密情報をリポジトリに入れない。** `SUPABASE_SERVICE_ROLE_KEY` と `ADMIN_TOKEN` はサーバー専用。
  `.env` は `.gitignore` 済みだが、コミット前に `git diff --cached` で混入を確認する。
  会話やログに貼るのも避ける。なお `index.html` の anon キーは公開前提のもので、これは問題ない。
- **スタッフの氏名・勤務予定は個人情報。** 外部サービスに投げたり、公開される場所に貼らない。
  テストやサンプルには実名を使わない（`supabase/seed.sql` は架空の名前になっている）。
- **破壊的な SQL は実行前に見せる。** `delete` / `drop` / `update` を含む文は、
  何件に当たるかと影響範囲を添えて提示し、了解を得てから渡す。
- **在庫キー（`k`）は Supabase の商品名と完全一致でなければ無言で「－」になる。** 全角括弧と半角括弧、
  スペースの有無まで一致させる。エラーは出ないので気づきにくい。

## 分からないことは調べるか、聞く

このスキルは書いた時点の状態を写したもので、実物とずれることがある。
参照ファイルの記述とコードが食い違っていたら、**コードが正しい**。
気づいたらついでにこのスキルを直す。

判断が要る場面（どのスタッフを優先するか、締切をいつにするか、価格をいくらにするか）は
クリニック側の決めごとであってこちらが決めることではない。選択肢と影響を整理して渡し、
決めてもらう。
